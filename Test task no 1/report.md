# Меры реагирования и предотвращения

Примечание: за ос взят Linux

## 1. Меры немедленного реагирования (первый час)

### Мера 1. Заблокировать доступ злоумышленника

Заблокировать учетную запись svc-backup, удалить добавленный SSH-ключ из /root/.ssh/authorized_keys, удалить вредоносную cron-задачу с http://198.51.100.23/p.sh.

**Обоснование:** Учетная запись создана с UID 0 (root), к ней добавлен SSH-ключ, а cron-задача каждые 30 минут скачивает и выполняет скрипт с внешнего сервера.

### Мера 2. Изолировать хост от сети
Отключить сетевой интерфейс через облачную консоль (Security Groups) или на самом хосте, чтобы остановить эксфильтрацию данных. До отключения зафиксировать активные соединения командой netstat -tunap.

**Обоснование:** Зафиксирована передача 1.85 ГБ данных на внешний хост (10 событий network_egress).

### Мера 3. Собрать доказательства
Сохранить логи (/var/log/auth.log, /var/log/syslog), историю команд всех пользователей (.bash_history), все cron-задачи, список процессов и список учетных записей. Упаковать в архив для расследования.

**Обоснование:** Злоумышленник уже пытался замести следы (login history truncated), нужно сохранить все до отключения хоста.

## 2. Меры предотвращения

### Мера 1. Внедрить двухфакторную аутентификацию (MFA) для SSH
Настроить Google Authenticator, PAM-модуль на всех серверах с публичным SSH-доступом. Без TOTP-кода вход невозможен даже при правильном пароле. Это делает брутфорс бесполезным.

**Обоснование:**  Злоумышленник получил доступ методом брутфорса (38 неудачных попыток, затем успешный вход).

### Мера 2. Настроить автоматическую блокировку IP после неудачных попыток
Развернуть Fail2ban на всех серверах с настройками: блокировка IP после 3 неудачных попыток входа за 5 минут на 24 часа. Доверенные IP (офис, VPN) добавить в белый список.

**Обоснование:** 38 неудачных попыток с одного IP за 20 минут - блокировка наступила бы после 3-й попытки.

### Мера 3. Настроить мониторинг критических изменений системы
Развернуть Osquery на всех серверах с проверкой каждую минуту: создание учетных записей с UID 0, добавление SSH-ключей в authorized_keys, изменение файлов в /etc/cron*. При обнаружении — отправка алерта в SIEM или на почту.

**Обоснование:** После успешного входа злоумышленник создал root-аккаунт и настроил cron за 3 минуты. Мониторинг обнаружил бы это сразу.


## 4. Ложный след (ложноположительное срабатывание)


### Событие:
```
2016-12-10T03:00:01	Auth	sudo_command	TTY=none		COMMAND=/opt/backup/nightly.sh LOW
```
## Почему это выглядит подозрительно?

| Признак | Почему тревожно |
|---------|-----------------|
| **Действие** | Выполнение `sudo_command` от имени root |
| **Команда** | Запуск скрипта `/opt/backup/nightly.sh` |
| **Контекст** | Происходит на скомпрометированном хосте |

**На первый взгляд:** Злоумышленник выполняет команды с повышенными привилегиями.

## Почему это НЕ инцидент?

### Причина 1: Это легитимная бэкап-задача

Бэкап-скрипт запускался **каждый день в 03:00 задолго до взлома** (с 10 декабря).

Это обычная плановая задача, а не действие злоумышленника.


### Причина 2: Отсутствие вредоносных признаков

| Проверка | Результат |
|----------|-----------|
| Скрипт скачивает что-то из интернета? | Нет, команда вызывает локальный скрипт `/opt/backup/nightly.sh` |
| Скрипт отправляет данные вовне? | Нет, это внутренний бэкап на внутреннее хранилище |
| Скрипт создает новых пользователей? | Нет |
| Скрипт изменяет SSH-ключи? | Нет |
| Время необычное? | Нет, 03:00 — стандартное время для ночных бэкапов |


### Причина 3: Регулярность выполнения

В логах видно, что событие повторяется **каждый день в одно и то же время**:

```
2016-12-10T03:00:01 | sudo_command | COMMAND=/opt/backup/nightly.sh
2016-12-11T03:00:01 | sudo_command | COMMAND=/opt/backup/nightly.sh
2016-12-12T03:00:01 | sudo_command | COMMAND=/opt/backup/nightly.sh
2016-12-13T03:00:01 | sudo_command | COMMAND=/opt/backup/nightly.sh
2016-12-14T03:00:01 | sudo_command | COMMAND=/opt/backup/nightly.sh
```

Учетная запись скомпрометирована, но не каждое действие от ее имени — атака.
